## Этап 1. Hello World + git + CI/CD-скелет ✅ Завершено (03.09.2026)

Ваше требование — CI/CD и деплой с первого коммита, даже если внутри пока ничего нет. Делаем это раньше любой реальной функциональности.

1. **Создать пустой Blazor Server проект** (`dotnet new blazor -o FamilyBudget --interactivity Server`) и убедиться, что он запускается локально (`dotnet run`) — видим дефолтную страницу в браузере.
2. **Инициализировать git**, добавить `.gitignore` для .NET, запушить в новый репозиторий на GitHub.
3. **Минимальный CI**: GitHub Actions workflow, который на каждый push делает `dotnet restore` + `dotnet build`. Пока без тестов — их добавим на этапе 10.
4. **Деплой на Render**: Render не поддерживает .NET нативно (нативные runtime — только Node.js, Python, Ruby, Go, Rust, Elixir), поэтому деплоим через Docker — потребуется `Dockerfile` в корне репозитория. Подключить репозиторий, убедиться, что дефолтная страница Blazor открывается по публичной ссылке.
5. **Завести проект в Neon** и сохранить строку подключения (как secret в GitHub / переменную окружения в Render) — просто подготовить, в код пока не встраиваем, БД ещё не спроектирована.

**Контрольная точка этапа:** есть репозиторий, CI гоняет билд на каждый коммit, приложение (пусть и пустое) реально открывается по ссылке в интернете. Дальше можно спокойно наращивать функциональность, зная, что путь до продакшена уже работает.

## Этап 4. Подключение Neon к Render (сразу после Этапа 3, до фич) ✅ Завершено (04.09.2026)

Вынесено раньше специально: без этого шага любая фича, трогающая БД, будет ломать деплой на Render, а принцип с Этапа 1 — деплой всегда рабочий — иначе нарушается.

1. Применить уже готовую миграцию к Neon (`dotnet ef database update` с указанием production-строки подключения вместо локальной).
2. Прописать строку подключения к Neon как переменную окружения в Render — `ConnectionStrings__DefaultConnection` (двойное подчёркивание — так ASP.NET Core распознаёт вложенные настройки из переменных окружения).
3. Секрет никогда не коммитится в git — только как переменная окружения в самом Render.

**Почему это не мешает локальной разработке:** `appsettings.Development.json` читается только когда `ASPNETCORE_ENVIRONMENT=Development` (по умолчанию так и есть при `dotnet run` локально). На Render `ASPNETCORE_ENVIRONMENT=Production`, поэтому файл разработки там вообще не читается, а используется только переменная окружения. Два независимых, непересекающихся пути — локальная разработка (Docker Postgres) и продакшен (Neon) не мешают друг другу.

## Этап 5. Аутентификация + семейные группы

**Архитектурное уточнение (найдено при подготовке к этапу):** самодельная модель `User` из Этапа 3 конфликтует с ASP.NET Core Identity — переделываем в `ApplicationUser : IdentityUser<int>` (убираем самодельные `Email`/`PasswordHash`/`GoogleId`, Google-вход пойдёт через встроенную таблицу `UserLogins`). `DbContext` меняется с обычного на `IdentityDbContext<ApplicationUser, IdentityRole<int>, int>`. Требует пересоздания миграции с нуля (локально `dotnet ef migrations remove`, на Neon — `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`, т.к. реальных данных ещё нет).

**Вторая архитектурная деталь (тоже найдена заранее):** Login/Register/Logout нельзя делать обычными интерактивными Blazor-компонентами (`--interactivity Server`) — Identity ставит auth-cookie через HTTP-ответ, а к моменту, когда интерактивный компонент "оживает", заголовки ответа уже отправлены. Решение — задокументированный паттерн Microsoft: эти 2-3 страницы делаются как static SSR Razor-страницы (как в шаблоне `dotnet new blazor -au Individual`), остальное приложение остаётся Interactive Server как и было.

1. Пересоздать миграцию под новую модель (`ApplicationUser`, `IdentityDbContext`).
2. ASP.NET Core Identity с email/паролем — Login/Register/Logout как static SSR-страницы (см. выше), без внешних зависимостей, чтобы не блокироваться на настройке Google.
3. Экраны создания семейной группы и присоединения к существующей.
4. Отдельным подшагом — добавить Google OAuth поверх уже работающей Identity-аутентификации (регистрация OAuth-клиента в Google Cloud Console; технически это встроенная таблица `UserLogins`, а не самодельное поле).
