# Структура БД: веб-приложение учёта семейных расходов

Итог обсуждения Этапа 2 плана. Схема — концептуальная (сущности, поля, связи), без привязки к конкретному синтаксису EF Core/SQL — это будет Этап 3.

## Ключевые решения, зафиксированные в процессе обсуждения

- **Изоляция данных по семейным группам**: Продукты, Категории и Магазины — не общие на всё приложение, а свои у каждой FamilyGroup.
- **Цена — свойство покупки, а не продукта**: Product идентифицируется только названием (+ опционально категорией); цена хранится в Purchase, чтобы избежать дублирования продуктов при изменении цены.
- **Дата покупки обязательна**, по умолчанию — текущая дата на момент внесения.
- **Без абстрактных покупателей**: покупку можно приписать только реальному пользователю, состоящему в той же группе. По умолчанию — тот, кто вносит запись.
- **Один пользователь = ровно одна группа** (это закрывает открытый вопрос из ТЗ про множественное членство — членство только в одной группе, не в нескольких одновременно).
- **Приглашение в группу — одна постоянная ссылка на группу**, с возможностью перегенерации. Отдельного экрана создания группы нет: личная группа создаётся при регистрации, при выходе из группы создаётся новая личная «My Family».

## Таблицы

### FamilyGroup
| Поле | Тип | Комментарий |
|---|---|---|
| Id | PK | |
| Name | текст | |
| CreatedAt | timestamp | |
| InviteToken | uuid, **nullable**, уникальный индекс | токен ссылки-приглашения (добавлен на Этапе 5, миграция `AddFamilyGroupInviteToken`) |

**Токен приглашения:** `Guid?` в коде. `NULL` означает «ссылки ещё нет»: токен создаётся через `Guid.NewGuid()` при первом открытии страницы группы. Перегенерация записывает новый `Guid.NewGuid()`. Несколько `NULL` уникальный индекс не нарушают (PostgreSQL не считает `NULL` равными).

### ApplicationUser
**Обновление с Этапа 5:** заменяет прежнюю самодельную `User`. Наследуется от `IdentityUser<int>` (даёт готовые `Email`, `PasswordHash`, механизм внешних логинов через `UserLogins` — Google-вход больше не самодельное поле `GoogleId`, а штатный сценарий Identity).

| Поле | Тип | Комментарий |
|---|---|---|
| Id | PK (int) | из IdentityUser<int> |
| Email | текст | из IdentityUser |
| PasswordHash | текст, nullable | из IdentityUser, управляется Identity |
| UserName | текст | из IdentityUser (Identity разделяет UserName и Email — в простых сценариях обычно совпадают) |
| DisplayName | текст | наше кастомное поле |
| FamilyGroupId | FK → FamilyGroup, **not null** | наше кастомное поле, ровно одна группа на пользователя |

Плюс служебные таблицы Identity, появляющиеся автоматически через `IdentityDbContext<ApplicationUser, IdentityRole<int>, int>`: `AspNetRoles`, `AspNetUserRoles`, `AspNetUserClaims`, `AspNetRoleClaims`, `AspNetUserLogins`, `AspNetUserTokens`.

| Id | PK | |

| ParentCategoryId | FK → Category, nullable | самоссылка, произвольная глубина иерархии |

**Набор по умолчанию (Этап 6):** каждая новая группа получает дерево из 26 категорий (8 верхнего уровня); единственное определение в коде — `Services/DefaultCategories.cs`. Группам, существовавшим раньше, дерево досеяно миграцией с данными `SeedDefaultCategories` (только группам без категорий; в миграции — замороженная копия списка).

**Имена** могут повторяться, в том числе у соседних категорий — ограничения уникальности нет.

**Удаление категории** удаляет всё её поддерево (логика в приложении, `CategoryService`). У продуктов из удалённых категорий `CategoryId` становится `NULL` (`ON DELETE SET NULL`), покупки не затрагиваются.

### Purchase
| Поле | Тип | Комментарий |
|---|---|---|
| Id | PK | |
| ProductId | FK → Product, not null | |
| Price | numeric(10,2), not null | цена **за единицу** в этой покупке (не свойство продукта); может быть 0 и отрицательной — строка скидки |
| Quantity | numeric(10,3), not null, default 1 | дробное (до тысячных), строго > 0 |
| PaymentMethod | smallint, not null, default Card | enum: Card / Cash |
| Date | date, not null, default сегодня | не позже завтрашнего дня (UTC): более поздняя дата заменяется на завтрашнюю |
| StoreId | FK → Store, nullable | |
| UserId | FK → ApplicationUser, not null, default — тот, кто вносит запись | выбор ограничен участниками той же FamilyGroup |
| FamilyGroupId | FK → FamilyGroup, not null | продублировано намеренно — упрощает запросы для отчётов |
| Currency | varchar(3), not null, default EUR | из ТЗ — задел на будущую мультивалютность, в MVP не используется активно |
| Notes | текст, nullable | из ТЗ; у каждой позиции своя |

**Трата по позиции** = Price × Quantity.

**Скидки** — отдельные строки с отрицательной Price: скидка на товар — строка того же продукта (Quantity = 1), скидка на весь чек без привязки к товару — продукт «скидка» без категории. Учесть: если появится отчёт по количеству купленного, строки скидок посчитаются как штуки.

**Сейчас в базе** (миграция `InitialCreate`) Price и Quantity — `numeric` без точности; приводятся к `numeric(10,2)` / `numeric(10,3)` миграцией в задаче на сервис покупок.

## Правила, которые нельзя выразить обычным DB-constraint (нужна проверка на уровне приложения)

1. **Защита от зацикливания в иерархии категорий** (A → B → A). При изменении ParentCategoryId нужно проверять, что среди предков нового родителя нет самой категории — простого SQL CHECK для произвольной глубины не существует. Перенос категории к другому родителю пока не реализован.
2. **UserId в Purchase должен принадлежать той же FamilyGroupId**, что и сама покупка — стандартный FK это не ограничивает, нужна валидация в коде при сохранении.
3. **Вступление в другую группу:** разрешено только если пользователь — единственный участник своей текущей группы. Порядок: сначала пользователь переносится в новую группу (смена FamilyGroupId), потом удаляется старая личная группа вместе с данными. Обратный порядок нельзя: FK пользователя на группу каскадный, и удаление группы удалило бы самого пользователя. Обе операции — в одной транзакции; в её начале блокируется строка текущей группы пользователя (`SELECT ... FOR UPDATE`), чтобы одновременное вступление другого человека в эту группу не привело к удалению его аккаунта каскадом.
4. **Выход из группы:** разрешён, только если в группе есть другие участники. В одной транзакции создаётся новая личная группа «My Family» и пользователь переносится в неё; прежняя группа и её данные не меняются.

## Открытые вопросы, оставленные на будущее (не блокируют Этап 3)

- Проверено тестом (Этап 6): каскадное удаление группы с вложенными категориями работает, несмотря на Restrict у родителя категории. Не проверено: Restrict-связи Purchase→Product и Purchase→User — вступление в группу полагается на каскад; проверить, когда появятся покупки.
- Не решено: что происходит с покупками участника, который вышел из группы (Purchase→User — Restrict).
- Точный формат CSV для импорта через Cowork — теперь, когда схема есть, можно решать (Этап 9 по плану).
- Логика определения дублей при импорте — тоже Этап 9.
